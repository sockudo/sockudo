## C1 — P1: mutable version work grows with retained revisions under a store-wide write lock (M/C)

**Affected workload:** many concurrent mutable messages, long AI streams, mixed channels sharing the memory store; SQL mutation traffic also repeats append-count work.

**References:** [crates/sockudo-core/src/version_store/memory.rs:16](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/version_store/memory.rs:16), [crates/sockudo-core/src/version_store/memory.rs:228](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/version_store/memory.rs:228), [crates/sockudo-core/src/version_store/memory.rs:275](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/version_store/memory.rs:275), [crates/sockudo-core/src/version_store/memory.rs:340](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/version_store/memory.rs:340), [crates/sockudo-core/src/version_store/memory.rs:378](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/version_store/memory.rs:378); [crates/sockudo-core/src/versioned_messages.rs:270](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/versioned_messages.rs:270); [crates/sockudo-server/src/history/postgres/version_store/store_impl.rs:393](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/postgres/version_store/store_impl.rs:393).

**Mechanism:** each atomic mutation scans for latest, optionally scans idempotency/append counts, then validates the entire chain by rebuilding two hash sets. All of this, payload mutation and record copying happen while holding the memory store's single write lock across every app/channel. No network await is needed to cause contention: O(V) CPU work in this critical section blocks unrelated channels. `get_latest` also scans V records; `get_versions` collects and sorts the chain on each page. Postgres and MySQL count all prior appends inside the per-channel mutation transaction even for operations that do not need an append cap check. SQL stream locking itself is required by the current serial contract.

**Evidence:** the optimized actual-store probe with 256-byte fixed data recorded get-latest p50 0.451 µs at 16 revisions versus 2.635 µs at 1,024. Mutation p50 was 6.873 µs versus 77.837 µs in run 1. The mutation sample grows by 106 revisions including warmups; it is not a fixed-size percentile comparison. Requested allocation bytes per operation rose from 11,736 to 112,308. A second run is retained. The existing single-operation benchmark timings fall below their named timing budgets; those tests do not disprove revision-count scaling. No concurrent production contention measurement was made.

**Smallest improvement:** maintain latest pointer, append count, version identity membership and operation-id index per message; validate the incoming record against persisted invariants instead of rehashing all predecessors. Keep the full-chain validator for imports/conformance. Only after this, partition the memory store by app/channel with explicit lock order and stable stream lifecycle. For SQL, persist append count transactionally and avoid irrelevant count queries.

**Estimated benefit:** latest lookup becomes O(1) within the indexed message, mutation bookkeeping O(1)/O(log V), and independent channels can progress concurrently. Payload copying remains. Effort medium; risk medium/high.

**Required verification:** arbitrary imported version order, highest-serial winner (do not replace `max_by` with `last` without proving order), duplicate version/delivery serials, operation-id conflict/replay, concurrent same-message and cross-channel writes, deletion, terminal appends, caps, purge/index repair, actor parity and contiguous replay. Run core version-store tests, backend atomic-mutation tests and concurrent HTTP/WS conformance.

## C2 — P1 for long streams: every append retains another complete accumulated string (M/C)

**References:** [crates/sockudo-core/src/versioned_messages.rs:203](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/versioned_messages.rs:203), [crates/sockudo-core/src/version_store/memory.rs:133](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/version_store/memory.rs:133), [crates/sockudo-core/src/version_store/memory.rs:353](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/version_store/memory.rs:353), [crates/sockudo-core/src/version_store/types.rs:373](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/version_store/types.rs:373); SQL serialization [crates/sockudo-server/src/history/postgres/version_store/store_impl.rs:437](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/postgres/version_store/store_impl.rs:437); DynamoDB [crates/sockudo-server/src/history/dynamodb/version_store/store_impl.rs:574](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/dynamodb/version_store/store_impl.rs:574).

**Mechanism:** `apply_append` constructs full state plus the original fragment, and each stored revision owns that full state. For n equal fragments of f bytes, retained data alone is f*n*(n+1)/2 rather than f*n. Arc sharing between the memory replay/message indexes avoids duplicating a revision across indexes; it does not share growing string prefixes between revisions. Durable backends serialize full version records; envelopes and idempotency receipts can add further copies. Egress rollup does not remove this storage cost.

**Evidence:** actual MemoryVersionStore readback after 2,000 × 64-byte appends returned 2,001 versions, 128,000 bytes latest data and 128,064,000 bytes summed historical data. At 128/512 appends, the corresponding sums were 528,384/8,404,992 bytes. These are data-byte counts, not RSS or disk usage. Whole-probe peak RSS is separately recorded and includes all probes/allocator retention.

**Smallest coherent improvement:** first enforce and observe existing append/accumulation/retention budgets. A material representation improvement requires original operation records plus bounded periodic snapshots and a latest-state cache. Reconstruct the exact public full-state version on reads. This is a design change, not a safe one-line clone removal, and should follow the lower-risk indexing work in C1.

**Estimated benefit/tradeoff:** disk/RAM growth closer to O(n*f + snapshots); additional reconstruction CPU/latency and more complicated purge/compaction. Effort high, regression risk high. Do not shorten retention, discard original appends, or persist rollup output to claim this benefit. Verify every original mutation remains available to history, recovery, webhooks and push; preserve four serial identities, idempotency, terminal state, random historical reads and crash recovery. Link design to `docs/specs/ai-transport-wire-protocol.md`.

## C3 — P1: annotation publishes rebuild the whole projection (M/C)

**References:** [crates/sockudo-core/src/annotations/memory.rs:121](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/annotations/memory.rs:121), [crates/sockudo-core/src/annotations/memory.rs:151](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/annotations/memory.rs:151), [crates/sockudo-core/src/annotations/memory.rs:223](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/annotations/memory.rs:223); [crates/sockudo-core/src/annotations/types.rs:274](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/annotations/types.rs:274); [crates/sockudo-adapter/src/handler/annotations.rs:91](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-adapter/src/handler/annotations.rs:91); durable loaders [crates/sockudo-server/src/history/postgres/annotation_store.rs:214](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/postgres/annotation_store.rs:214), [crates/sockudo-server/src/history/mysql/annotation_store.rs:357](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/mysql/annotation_store.rs:357), [crates/sockudo-server/src/history/dynamodb/annotation_store.rs:580](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/dynamodb/annotation_store.rs:580), [crates/sockudo-server/src/history/scylla/annotation_store.rs:397](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/scylla/annotation_store.rs:397).

**Mechanism:** appending snapshots all retained events for that message/type, sorts and replays them through duplicate/delete handling and summarization. Optimistic memory projection rebuild retries if a concurrent append changes its serial. Total summarizers are cheap, but the surrounding validation/replay is not. Supplied annotation IDs can trigger an additional full `get_events` preflight in the adapter. SQL and document implementations also load projection event sets; they have explicit bounds (100k SQL, 10k Dynamo/Scylla), so do not describe those as infinite.

**Evidence:** duplicate append with a fixed retained projection isolates rebuild work: p50 19.046 µs / 216.209 µs / 2.546 ms at 100 / 1,000 / 10,000 events, requesting 13,040 / 170,032 / 1,389,696 allocation bytes per call. Same-serial duplicate avoids changing the measured size; it does not measure new-insert I/O. Run 2 and p95/p99 are retained. Accumulating n annotations performs roughly quadratic total replay work (plus sorting), and concurrent retry amplification is code-backed, unmeasured.

**Smallest improvement:** cache duplicate outcomes without rebuilding; maintain create-ID lookup and incremental summarizer state for in-order inserts/deletes, with full rebuild for out-of-order imports, revision conflict or repair. Start with the simplest summarizer but preserve its canonical duplicate/delete semantics. Bound rebuild concurrency per projection.

**Estimated benefit/tradeoff:** normal publication cost tied to the new event and changed summary instead of all A events. More index/state memory, recovery complexity; medium/high effort and risk. Verify all five summarizers, create-ID conflicts, deleting old/nonexistent IDs, raw annotation gating, summary projection revision ordering, retention/purge, concurrent first create/delete and independent annotation authorization.

## C4 — P1 at churn: presence history repeatedly scans/rebuilds retained state (M/C)

**References:** [crates/sockudo-core/src/presence_history/memory.rs:131](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/presence_history/memory.rs:131), [crates/sockudo-core/src/presence_history/memory.rs:185](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/presence_history/memory.rs:185), [crates/sockudo-core/src/presence_history/memory.rs:215](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/presence_history/memory.rs:215); [crates/sockudo-core/src/presence_history/durable.rs:239](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/presence_history/durable.rs:239), [crates/sockudo-core/src/presence_history/durable.rs:326](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/presence_history/durable.rs:326); wiring [crates/sockudo-server/src/presence_history.rs:25](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/presence_history.rs:25).

**Mechanism:** after any memory event eviction, the entire retained deque is replayed into `latest_event_by_user` under the global write lock. At a steady count cap this happens on every new transition. The durable wrapper first inspects the stream and retains over both cache maps on each transition. A previously unseen user's cache miss scans history pages until finding the user/dedupe key or exhausting history, decoding records and acquiring the cache lock per record. New-user churn can therefore pay O(H) history work per join, and memory linear-page seeking can compound it.

**Evidence:** 101 unique-user insert samples with a count cap: p50 5.039 µs at 100 retained events, 76.694 µs at 1,000, 1.114 ms at 10,000; comparable uncapped insert p50 ~0.661 µs. Uncapped history grows by 101 during sampling; capped history stays at H. This measures the memory implementation, not remote durable latency. Durable round trips are code-backed only.

**Smallest improvement:** maintain per-user last retained serial/state and repair only a user whose indexed record was evicted. For durable dedupe, introduce authoritative indexed transition lookup or a persisted per-user transition state in the same durable abstraction; track the cached retained watermark and prune only when it advances. Avoid assuming a cache miss means no prior transition across nodes.

**Estimated benefit:** steady capped inserts no longer rebuild H entries; new-user durable checks become bounded indexed reads. Extra index state and cross-node consistency work, medium/high risk. Verify duplicate disconnects, multiple connections per user, first join/last leave, node loss, stream reset, retention boundary, degraded-store behavior and historic snapshot reconstruction. Current presence membership must remain independent of durable history availability.

## C5 — P2: memory history page cost depends on cursor depth and locks out other channels (M/C)

**References:** [crates/sockudo-core/src/history/memory.rs:51](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/history/memory.rs:51), [crates/sockudo-core/src/history/memory.rs:172](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/history/memory.rs:172), [crates/sockudo-core/src/history/memory.rs:219](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/history/memory.rs:219), [crates/sockudo-core/src/history/memory.rs:248](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/history/memory.rs:248); analogous presence paging [crates/sockudo-core/src/presence_history/memory.rs:301](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/presence_history/memory.rs:301).

**Mechanism:** page reads take a store-wide write lock to evict, then walk from a deque end and filter to the cursor/bounds. Reading all H records in pages of L can visit O(H²/L) records. Returned payload Bytes are shared, so do not count them as payload-size clones.

**Evidence:** first 100-item page remains ~9.8 µs across 1k–100k records. Near-tail oldest-first page grows to p50 143.361 µs, p95 152.448 µs at 100k versus first-page p50 9.798 µs. These are isolated store latency samples, not socket latency or concurrent lock measurements.

**Smallest improvement:** seek by canonical serial using a suitable ordered/range index (or binary search if the insertion invariant is made explicit), then iterate only the required candidates. Preserve time-bound handling with clock skew. Split channel locks after defining eviction/reset lock order.

**Estimated benefit:** O(log H + L) serial-bounded pages and reduced lock tenure; index memory/insertion cost. Verify gaps, out-of-order append evidence, both directions, expired cursors, reset/purge, mixed time bounds, empty sparse pages, rewind, replay and until_attach. Effort medium, risk medium/high.

## C6 — P1: durable history maintenance rereads retained data on every append (C)

**References:** Postgres [crates/sockudo-server/src/history/postgres/writers.rs:88](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/postgres/writers.rs:88), [crates/sockudo-server/src/history/postgres/writers.rs:191](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/postgres/writers.rs:191), [crates/sockudo-server/src/history/postgres/writers.rs:254](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/postgres/writers.rs:254); MySQL [crates/sockudo-server/src/history/mysql/writes.rs:11](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/mysql/writes.rs:11), [crates/sockudo-server/src/history/mysql/writes.rs:120](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/mysql/writes.rs:120), [crates/sockudo-server/src/history/mysql/writes.rs:185](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/mysql/writes.rs:185); DynamoDB [crates/sockudo-server/src/history/dynamodb/writes.rs:56](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/dynamodb/writes.rs:56), [crates/sockudo-server/src/history/dynamodb/queries.rs:35](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/dynamodb/queries.rs:35); Scylla [crates/sockudo-server/src/history/scylla/entries.rs:169](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/scylla/entries.rs:169); Surreal [crates/sockudo-server/src/history/surreal/entries.rs:131](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/history/surreal/entries.rs:131).

**Mechanism:** SQL writers insert then evict/count/aggregate channel history and update metadata per record. Byte caps fetch all serial/size rows. Postgres performs at least BEGIN, INSERT, age DELETE, aggregate SELECT, two UPDATEs and COMMIT even without count/byte caps. DynamoDB rereads **all payload-bearing records** across pages to recompute retention; Scylla/Surreal read the full metadata list. Document eviction repeatedly removes vector element zero and individually awaits deletes. Costs scale O(H) per publish (Dynamo O(H*payload)) plus O(E*H) shifts and E delete round trips when evicting E records. Postgres/MySQL execute this in their asynchronous bounded writer queues, so the immediate cost is drain throughput and history lag rather than necessarily synchronous HTTP latency. Other backends execute maintenance on their append path. Queue pressure and lag can become continuity/degraded-state issues.

**Smallest improvement:** a metadata-only Dynamo projection is an immediate contained reduction in network bytes. Then track exact retained count/bytes incrementally with idempotent insert outcomes and batched bounded eviction; use one prefix drain instead of repeated remove(0), and backend-safe bounded delete batches. Coalesce adjacent compatible append work within an existing writer with a byte/record/deadline bound. Do not simply increase queue capacity.

**Estimated benefit/tradeoff:** maintenance proportional to changed/evicted records rather than all retained rows; fewer commits/round trips. Batching adds bounded latency and may change failure granularity. Medium/high effort, high correctness risk. Preserve app/channel isolation, retention overrides, cross-node updates, serial generation, idempotent replay, durability acceptance contract and degraded/reset-required transitions. Inspect EXPLAIN/DB read bytes at H=1k/10k/100k, 256B/4KiB/64KiB records, cap disabled/count/bytes, 1/8/32 publishers. Measure queue age as well as depth. No database benchmark was executed.
