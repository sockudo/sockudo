## Main execution paths and dimensions

- HTTP/WS auth and webhook processing call `AppManager.find_by_key/find_by_id`. Outer CachedAppManager first clones a full App from an ID/key local index, then shared JSON cache, then backend, then repopulates both cache keys. TTL invalidation or invalid identifiers bypass warm hits. Cost scales with concurrent cold lookups, app policy size, and total applications for enumeration.
- `GET /up` enumerates all apps, which invokes backend listing and outer-cache warming; push repair does the same per repair pass. These are background/probe paths coupled to shared cache and DB throughput.
- Lifecycle/message webhooks build JobData and either enqueue immediately or append to the timer batch vector. Queue workers resolve current app webhook configs, filter events per endpoint, serialize/sign filtered bodies, acquire a shared 20-permit semaphore, then deliver HTTP/Lambda. Queue capacity, retry duration, endpoint count, and event arrival rate interact.
- General queues provide webhooks and the server push bridge. Memory admits into bounded ready/delayed/active/DLQ state but retains dedup separately; Redis uses per-logical-queue cluster hash tags and bounded per-worker prefetch with renewable leases; broker adapters use native persistence and ACK/DLQ rules. SNS has no consumer. Backend semantic differences preclude blanket parallelism/retry changes.
- AI orphan sweeper repeatedly calls `scan_prefix_page` over active-stream registry entries until exhaustion. Redis scans issue per-key fetches; memory rebuilds a full sorted matching list per page.
- Rate-limiter middleware awaits atomic admission before invoking the handler. Redis failures are retried by each requesting task independently. Metrics are recorded throughout WS receive/send, HTTP, fanout, persistence, annotations and queue mechanics; facade wrappers allocate labels for every call and some annotation labels retain raw channel/type values indefinitely.

### S1 — P1: Memory queue admission rescans all retained deduplication keys

References: [enqueue cleanup under lock](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/memory_queue_manager.rs:166), [full-map retain](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/memory_queue_manager.rs:218), [dedup insertion](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/memory_queue_manager.rs:194), [push bridge keys](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/bootstrap/push/queue.rs:266), [defaults](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/options/queue.rs:120).

Every enqueue takes the per-queue lock and calls `HashMap::retain` over D dedup entries, even when the new job has no dedup key. Push bridge message IDs advance per produce/retry, so distinct retained keys accumulate. With TTL T and admission rate r, D approaches rT (subject to workload/throughput), while total full-map checks over filling D entries are quadratic. Ready capacity and completed retention do not cap the live dedup map; expired entries are only removed on subsequent admission. CPU spent in retain blocks all producers for that logical queue.

Evidence: real public-API diagnostic [memory_queue diagnostic](/home/radud/Desktop/Code/Rust/sockudo/audits/performance-2026-09-05/diagnostics/src/bin/memory_queue.rs). It compares equal ready-queue sizes with zero versus 1k/10k/30k live dedup keys, then times 500 ordinary enqueues over three samples. Measured result: at 30k seeded entries, 500 probe enqueues took 14.658–14.708ms with retained dedup keys versus 0.251–0.261ms for an equal-sized ready queue seeded without dedup. At 10k dedup keys the probes took 4.016–4.028ms. This isolates sensitivity to retained dedup state, not a production speedup from an implemented fix. [Raw samples](/home/radud/Desktop/Code/Rust/sockudo/audits/performance-2026-09-05/results/memory-queue.txt). Reproduce: `cargo run --locked --offline --release --manifest-path audits/performance-2026-09-05/diagnostics/Cargo.toml --target-dir target --bin memory_queue`. The preload is excluded from timing and no callbacks/Redis are involved.

Smallest fix: expiration-ordered index (e.g. existing BTreeMap pattern or min-heap) and bounded removal of due keys instead of per-enqueue full retain; keep direct HashMap dedup lookup. Store an expiry generation/value so stale index entries cannot remove a refreshed key. Expected benefit: admission cost becomes independent of live unexpired D except hash lookup and expiry-index insertion, estimated rather than production measured. Effort medium, correctness risk medium: test exact TTL boundary, duplicate keys, repeated IDs/payload mismatch, retries, completed retention, concurrent enqueue, saturated queue, capacity and expired index cleanup. Avoid silently shrinking dedup window.

### S2 — P1/P2: Readiness probes and push repair rewrite the entire application cache

References: [general `/up`](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/http_handler/system.rs:418), [Cached get_apps](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-app/src/cached_app_manager.rs:385), [cache_app serial writes](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-app/src/cached_app_manager.rs:245), [index clear](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-app/src/cached_app_manager.rs:106), [repair pass](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-server/src/bootstrap/push/workers.rs:301).

Each `get_apps` fetches all backend apps, clears/rebuilds both local indexes, then calls `cache_app` sequentially for each app; `cache_app` clones the app again, serializes twice and awaits two shared-cache SETs. For A applications and RTT R, healthy shared-cache warm time includes roughly 2AR serial RTT, plus whole-list DB I/O and policy clones. Every health probe amplifies this work; a timeout can report an otherwise healthy deployment unhealthy and briefly emptied indexes can create concurrent lookup misses. The 100ms timeout is per cache operation, not a bounded full list. Push repair startup/ticks contend for the same resources.

Evidence: direct call chain; the supplied cache/app mock diagnostic establishes underlying SET costs but does not exercise complete `/up`. Reproduce with A=1/100/1000 and local vs network Redis, repeated `/up`, record endpoint latency, Redis `commandstats` SET count, DB calls and cache-miss counters. Use a dedicated fixture app list; expected SET count 2A per successful call is code-backed. No live health-load numbers claimed.

Fix: use a lightweight app-presence/health query for readiness rather than materializing and warming every app; make enumeration populate local entries incrementally and bulk/bounded shared-cache warming only when required. Preserve `/up`'s no-app/disabled/error statuses and fresh app discovery for repair. Do not replace a health check with an arbitrarily stale cached success. Benefit: removes app-count-dependent network writes from readiness (estimated), and reduces repair overhead. Effort medium, risk medium (readiness semantics and cache invalidation).

### S3 — P2: Cold app lookups have no request coalescing or bounded negative cache

References: [ID miss](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-app/src/cached_app_manager.rs:282), [key miss](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-app/src/cached_app_manager.rs:306), [shared-cache timeout](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-app/src/cached_app_manager.rs:14), [post-miss double writes](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-app/src/cached_app_manager.rs:245).

C simultaneous cold/expired lookups independently read the shared cache and call the DB. Each positive response writes both cache keys independently; unknown keys are never remembered, so repeated invalid-key traffic keeps hitting DB. TTL waves/reconnect storms amplify the backing DB pool queue and serialized cache round trips. Internal SQL/Surreal cache checks also use get-then-load rather than coalesced load; SQL key lookup lacks that inner hit check entirely. Warm local hits already avoid shared cache and must remain fast.

Evidence: [services diagnostic](/home/radud/Desktop/Code/Rust/sockudo/audits/performance-2026-09-05/diagnostics/src/bin/services.rs) real CachedAppManager plus mocked 20ms backend / 2ms cache SET, concurrency 1/32/128, existing/missing apps, 3 samples. Measured: each 128-request positive cold wave made 128 backend calls, 128 shared GETs and 256 SETs (three samples), taking 27.656–27.763ms with mocked I/O; all four sequential warm followups hit local cache. Every unknown-key wave likewise made 128 backend calls, and four followups made four more backend calls. [Raw samples](/home/radud/Desktop/Code/Rust/sockudo/audits/performance-2026-09-05/results/services.txt). Reproduce: `cargo run --locked --offline --release --manifest-path audits/performance-2026-09-05/diagnostics/Cargo.toml --target-dir target --bin services`. No live DB latency extrapolation. Smallest fix: per-key in-flight coalescing of authoritative loads (bounded lifetime/state), serialize once and bulk/parallel cache ID/key writes; optionally bounded short negative entries with create/key-rotation invalidation. Benefit: C same-key backend loads can reduce to one per process wave, estimated outside controlled mock. Correctness: invalidate both key indexes on update/delete; ensure cancellation does not strand waiters, error is not cached as absent, transient DB faults are not negative-cache hits, newly created/rotated app keys become valid promptly. Effort medium/risk medium.

### S4 — P2: AI registry pagination repeatedly processes the entire keyspace

References: [memory collect/sort](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-cache/src/memory_cache_manager.rs:131), [Redis per-key GET](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-cache/src/redis_cache_manager.rs:274), [cluster per-key GET](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-cache/src/redis_cluster_cache_manager.rs:250), [AI sweep caller](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-adapter/src/handler/ai_orphans.rs:203).

Memory `scan_prefix_page` iterates all N cache entries, collects K matches including owned values, sorts K by key, locates cursor, and clones the returned slice. With page limit L, a full sweep repeats this approximately K/L times: O((K/L)(N+K log K)) time and O(K payload bytes) temporary storage per page. Iterator-owned String values mean unrelated entries also require consideration for allocation profiling. Redis and cluster make a SCAN then sequential GET for every key, yielding K extra RTTs per full sweep. The caller is a background janitor, not every publish, but it shares Tokio workers, cache, and Redis with active streams.

Evidence: supplied real MemoryCacheManager diagnostic times first page and full sweep for K=1k/5k/10k, values 64B/4KiB, L=256, 3 repeats, verifies exact returned count. Measured full memory sweep: 1k/64B entries 0.572–0.614ms; 10k/64B 66.175–67.321ms; 10k/4KiB 368.025–384.294ms (40 pages), three samples each. [Raw samples](/home/radud/Desktop/Code/Rust/sockudo/audits/performance-2026-09-05/results/services.txt). Reproduce using the `--bin services` command under S3. These are sweep costs, not production improvement estimates. For Redis, run same cache fixture against a dedicated local/latency-injected Redis instance and record command counts/latency; no runtime Redis claim here.

Fix: memory ordered key index or a bounded scan strategy that does not rebuild all sorted values every page; clone values only for selected page. Keep cursor opaque and stable under mutation/expiry. Redis: bounded pipeline GETs (or suitable MGET for standalone); cluster must route by slot and must not introduce CROSSSLOT assumptions. Root/fanout should also examine distributed scan semantics before changing cluster cursor behavior. Benefit: bounded page work and O(K) rather than K serial fetch RTTs, estimated. Risk: pagination duplicates/misses when mutating, expired keys, cluster completeness; test until cursor exhaustion, concurrent insert/delete, terminal cursor, no infinite restart, orphan closure exactly once/serial checks. Effort medium.

### S5 — P1/P2: Annotation metric cardinality grows with channel/type churn and survives state cleanup

References: [annotation raw labels](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-metrics/src/prometheus/driver.rs:1013), [recording](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-metrics/src/prometheus/interface.rs:516), [live mutation caller](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-adapter/src/handler/annotations.rs:162), [rebuild on subscribe](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-adapter/src/handler/subscription_management.rs:968), [recorder options](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-metrics/src/prometheus/recorder.rs:48), [render](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-metrics/src/prometheus/interface.rs:666).

Annotation counters and histogram use raw channel (and sometimes annotation type), without an idle-series policy or explicit eviction. V2 per-room/per-message channel churn leaves new series for every historical channel/type even after application state disappears. Histogram adds bucket/count/sum series per label set. This increases recorder heap, CPU to render each scrape, network scrape size, and downstream storage. Existing channel-subscription/broadcast metrics already bucket names; do not claim all metrics are unbounded. Raw delta helper metric definitions exist but current production call sites were not found, so not included in active growth claim.

Reproduction procedure: on a single `PrometheusMetricsDriver`, record annotation publish/rebuild/duration for 1k/10k/100k distinct synthetic channels, let channel records go out of scope, render repeatedly; measure RSS, output lines/bytes and elapsed render time. Or perform same on V2 annotation API against isolated fixtures. This is not yet runtime measured. Fix: low-cardinality aggregate metrics (channel class plus app/finite type), or explicitly opt-in capped detailed channels and idle eviction. Existing dashboards are a compatibility surface: preserve/migrate metric names/labels with documentation and checks. Estimated benefit linear reduction in churn-dependent memory/scrape growth. Effort medium, operational regression risk medium; no protocol change.

### S6 — P2: Metrics wrapper recreates owned label vectors and facade registrations per event

References: [labels_from_iter](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-metrics/src/prometheus/handles.rs:8), [CounterVec lookup](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-metrics/src/prometheus/handles.rs:122), [facade call](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-metrics/src/prometheus/handles.rs:137), [get_tags](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-metrics/src/prometheus/driver.rs:1451), [WS receive/send](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-metrics/src/prometheus/interface.rs:164), [receive call](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-adapter/src/handler/mod.rs:1084).

Per WS event, `get_tags` builds Vec<String> for app/port; each counter copies metric name, collects an intermediate vector of borrowed values, then copies both label names and values into another vector. Update clones metric name again and invokes metrics-rs dynamic registration/lookup, whose owned-key path can add further copying. Two counters are updated per WS send/receive. Similar churn affects each rate-limit check, history mutation, etc. Thus instrumentation alone performs many small allocations per event despite stable app/port labels. Some fanout callers already use batch marks; preserve them.

No allocation number asserted without measurement. Reproduce by warmed loop of `mark_ws_message_received`/`mark_ws_messages_sent_batch` with metrics enabled, one then many apps, using allocator counter and CPU profiler; compare equal counter results against cached `metrics::Counter` handles. Root can instrument public driver. Fix: pre-register/cached handles for bounded app/port/operation combinations, store port once, use static label names, remove redundant label copies; cap lifecycle/cache cardinality. Expected reduction O(events) allocations/registration work, estimated. Effort small-medium; risk low if labels/counters exactly preserved and recorder fanout still sees all updates.

### S7 — P1: Optional webhook batching bypasses queue backpressure with an unbounded vector

References: [buffer field](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-webhook/src/integration.rs:112), [timer takes and awaits batch enqueue](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-webhook/src/integration.rs:186), [unconditional push](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-webhook/src/integration.rs:222), [size applied only when splitting](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-webhook/src/integration.rs:201).

When batching enabled, producers append immediately and return success regardless of backlog. Batch size controls splitting after each timer tick, not vector capacity or early flushing. While the sole timer awaits a slow broker enqueue, all incoming events accumulate in a replacement Vec. At arrival rate r and blocked duration T, retained jobs grow rT (plus the already-drained batch) and hold full JobData payloads/credentials; there is no job/byte bound. On queue-full error the drained batch is merely logged/dropped. This defeats queue capacity, worsens dependency outages, and has a correctness consequence alongside OOM risk. AI lifecycle explicitly bypasses this vector through `add_bounded_webhook`; do not conflate AI lifecycle with ordinary batched webhooks.

Reproduce: construct integration with batching enabled, 50ms duration, size 100 and a mock QueueInterface whose batch enqueue waits on a Notify. Send one event, wait for flush to block, then continuously `send_member_added`/client events and track return count/RSS. Existing `webhook_hot_paths` times buffer pushes but doesn't test blocked drain. No measured RSS claim. Fix bounded job AND byte budget via channel or current vector accounting, flush on size or timer, propagate/admit backpressure and recover enqueue failures without silently dropping. Own cancellable task and graceful drain. Benefit: provably bounded memory during slow broker, estimated throughput/latency impact; latency may increase or admission can fail under saturation. Preserve per-app event order, HMAC bodies, existing V1 webhook format, AI original-mutation delivery and retry semantics. Effort medium, risk medium.

### S8 — P2: Redis queue round-robin prefetch stalls behind a full individual worker

References: [per-worker bounded channels](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/redis_backend.rs:790), [global free-capacity sum](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/redis_backend.rs:967), [round-robin awaited send](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/redis_backend.rs:1018).

Prefetch sums free slots over all workers to decide claim count, but delivers to next_worker unconditionally then awaits its send. A long-running callback fills that worker's private queue while other workers drain theirs; once next_worker is full the only prefetch task blocks, so later jobs cannot reach idle workers. Leases for not-yet-sent jobs are already claimed and renewed. Variable webhook latency/push work makes this realistic; total free capacity is not sufficient to prevent HOL. Existing fixed-delay queue benchmark hides skew.

Reproduce using a local Redis queue, concurrency 4/prefetch 1 then 16, 1% callbacks delayed 1s and rest immediate; record worker idle time, queue age and throughput vs uniform delay. Existing command baseline: `cargo run --release -p sockudo-queue --features redis,redis-cluster --example queue_bench -- redis 10000 4 1000` (the example needs a skewed-delay extension; no skewed run claimed). Fix choose a sender with available capacity/reserve using fair retry, or a bounded shared dispatcher/work-stealing queue; never exceed configured callback concurrency or renew leases after lost ownership. Ordering is already concurrent, but verify per-job idempotency, shutdown while sender full, lease renewal, retry settlement, no skipped or duplicate lost jobs. Effort medium, risk medium, estimated gain specific to heterogeneous callbacks.

### S9 — P2: Kafka and Iggy consumers serialize all callbacks on one receive loop

References: [Kafka one partition](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/kafka_queue_manager.rs:89), [empty key](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/kafka_queue_manager.rs:134), [callback plus retry sleep](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/kafka_queue_manager.rs:215), [Iggy callback before next receive](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/iggy_queue_manager.rs:216), [Iggy offset store](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/iggy_queue_manager.rs:219).

Kafka processes one job and all its retry sleeps before reading another; Iggy awaits callback and offset storage in the receive loop. For average callback time C and ACK time A, throughput per consumer is bounded near 1/(C+A), regardless of backlog/prefetch. A slow webhook can stop all work on that consumer; Kafka's automatically created single-partition topic limits consumer-group scaling too. Current serial design protects offset ordering; don't call it a simple missing JoinSet or recommend unguarded parallel commits. Docs explicitly limit concurrent prefetch support to other backends.

Reproduce broker-specific fixture 1000 jobs with 10/100ms callbacks, multiple partitions, and one poison/slow job; compare callback concurrency and partition progress. Live broker missing here. Smallest improvement: per-partition serial workers with bounded concurrency across partitions and commit watermarks; allow queue partition configuration with an explicit key strategy. For order-independent general queue work, bounded within-partition execution requires contiguous completion offsets and documented guarantees. Expected benefit depends on partitions and payload work; estimated. Effort high, regression risk high; lower implementation priority than other findings.

### S10 — P2: Some broker retry paths immediately recycle failed work

References: [RabbitMQ same-queue republish](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/rabbitmq_queue_manager.rs:310), [Iggy republish](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/iggy_queue_manager.rs:555), [SQS visibility zero](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/sqs_queue_manager.rs:564), [Pub/Sub nack](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-queue/src/google_pubsub_queue_manager.rs:250).

RabbitMQ/Iggy use max attempts but republish immediately without configured delay/jitter. SQS releases visibility to zero on failure; redrive policy is external and can be absent. Google subscription creation does not set retry policy and callback failures nack immediately (actual broker redelivery pacing requires measurement). During a dependency outage, admitted rate r can multiply callback/broker traffic by max_attempts in a short burst for bounded retries; SQS/Google can repeatedly cycle until external policy stops them. Default global retry_base=1s/max=60s/jitter=.2 do not pace these paths. NATS already uses delayed NAK; Redis/memory already schedule delayed retries.

Reproduction: controlled callback always fails quickly, count deliveries and broker publish/receive/ACK/visibility operations per second with configured max_attempts and delay=1s, then restore callback and assess recovery backlog. No broker runtime tested. Fix use backend-native delay/redelivery/retry queues/backoff with bounded outstanding retry state, or explicitly configure/document external policy and reject unsupported requested guarantees. Never sleep holding the only Kafka consumer or unbounded task per failed job. Risk: durable retry timing and DLQ transfer loss/duplicate semantics; test broker loss during republish, attempt preservation, max attempts and no hot loops. Effort backend-dependent medium/high. Estimated benefit reduces outage amplification, not claimed healthy-path gain.

### S11 — P2: Redis limiter recovery fans out fresh connections per failed in-flight request

References: [standalone recovery](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-rate-limiter/src/redis_limiter.rs:130), [cluster recovery](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-rate-limiter/src/redis_cluster_limiter.rs:103), [fresh means new manager](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-core/src/redis_client.rs:179), [middleware awaits](/home/radud/Desktop/Code/Rust/sockudo/crates/sockudo-rate-limiter/src/middleware.rs:207).

### S13 — P2: Slow webhook retries monopolize the shared endpoint concurrency pool

Retry pacing has no jitter, making waves synchronize. Error responses are fully buffered via `response.text()` even though discarded; large/slow error bodies add memory and extend permit holding. A request timeout limits duration, not response bytes.

Evidence code-backed; reproduce local HTTP fixture with 20 endpoints returning immediate 503 and one immediate 204 healthy endpoint, compare healthy job latency to no-failure control; vary error body 0/1MiB/10MiB. Must use actual sender and record total in-flight requests/queue depth. No latency numbers claimed. Fix separate active-request semaphore from bounded retry-state/queue scheduling, with fair per-endpoint/app budgets; add jitter and bounded response drain/discard; keep reqwest client reuse. Releasing semaphore alone without bounding retry jobs is insufficient. Correctness: do not falsely ACK before durable retry acceptance; preserve signatures and payload across attempts, retry policy/budget/status semantics, duplicates/idempotency. Effort medium-high and moderate risk; prioritize unbounded batching first.

## Lower-priority observations / intentionally not promoted

- FallbackCacheManager does serialize every operation with Mutex across await and synchronizes every fallback entry under recovery write lock; CacheManagerFactory explicitly avoids it because coordination must fail closed. Public library-only optimization unless callers wire it manually; no server impact attributed.
- SQL app `find_by_key` always hits DB if the outer cache decorator is disabled, despite an ID-only local Moka cache; workload and configuration dependent, not a reason to bypass app security freshness.
- DynamoDB get_apps scans only one response page (correctness gap), Scylla reads use indexed key queries and session paging; do not turn every whole-list API into a performance defect without a caller (S2 supplies the actual caller).
- MemoryRateLimiter maps are cleaned by one global sweeper every 10s. Higher distinct-IP rate can increase memory within window+cleanup delay, but no independent substantive replacement justified by code alone.
- MemoryCacheManager uses count capacity, not byte weight, and has() clones a String via get. Impact depends on actual cached values; S4 is the stronger concrete path.
- Metrics process scraping synchronously enumerates `/proc/self/fd` O(open FDs) and renders all series on async thread. Worth million-connection scrape profiling but lower priority than demonstrated cardinality/allocations; don't assume `spawn_blocking` automatically improves normal small scrapes.
- Optional broker producer first-use caches can duplicate initialization under simultaneous calls; steady-state successful handles are cached. Lower priority than Lambda's permanent per-job cache loss.
- No blanket allocator/lock/hash map replacement recommended; several potentially suspicious clones are deliberate retries, SDK handle clones, or bounded batches.
