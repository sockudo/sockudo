This page lists the metrics Sockudo exports, what each one tells you, and which conditions are worth
paging on. Set it up before production traffic: realtime failures are often silent (a node that stops
hearing its peers, a history store that degrades, a webhook queue that backs up) and only metrics
make them visible.

Observability is part of the runtime contract. A realtime system should tell operators when it is connected, degraded, delayed, retrying, or dropping work.

## Metrics endpoint

```bash
curl http://127.0.0.1:9601/metrics
```

Prometheus metrics are served on the dedicated `[metrics]` listener (`9601` by default), not on the
WebSocket and HTTP API port, so you can keep them on a private network.

```toml title="config.toml"
[metrics]
enabled = true
driver = "prometheus"
host = "0.0.0.0"
port = 9601

[metrics.prometheus]
prefix = "sockudo_"
```

Scrape the endpoint with Prometheus and label metrics by environment, region, node, adapter, and app where possible. Sockudo emits metrics through the `metrics-rs` recorder and exposes them through the Prometheus exporter by default.

How to read the tables below:

- Names assume the default `sockudo_` prefix. `process_*` metrics are never prefixed.
- Most Sockudo metrics carry `app_id` and `port` labels; extra labels are listed per metric.
- A counter only goes up: graph it with `rate()` or `increase()`. A gauge is a current value. A
  histogram exposes `_bucket`, `_sum`, and `_count` series: use `histogram_quantile()` for latency.
- Prometheus adds `instance` and `job` at scrape time; use `instance` to compare nodes.

For OTLP export of the same metrics plus traces and logs, see
[Observability configuration](/docs/reference/configuration#observability).

## TCP metrics exporter

For live debugging or sidecar consumers, Sockudo can also fan out metric events over TCP using `metrics-exporter-tcp`. This exporter streams protobuf-encoded metric events to connected clients; it is useful for local inspection and custom collectors, but Prometheus scraping should remain the primary production monitoring path.

```toml title="config.toml"
[metrics.tcp_exporter]
enabled = true
host = "127.0.0.1"
port = 5000
buffer_size = 1024
```

The TCP exporter has bounded buffering by default. When buffers fill, event samples can be dropped to avoid blocking the server, so do not use it as the only source for alerts or SLO dashboards.

## Core signals

| Area | Watch |
| --- | --- |
| Connections | active sockets, connection attempts, disconnects, connection errors by type |
| Subscriptions | subscribe and unsubscribe rates, active channels by type |
| Publish | HTTP calls, idempotency hits, rate-limit rejections |
| Fanout | broadcast latency, cross-node request latency, transport reconnects and drops |
| Recovery | resume successes by source, resume failures by code |
| History | writes, write failures, queue depth, degraded and reset-required channels |
| Webhooks | queue depth and settled outcomes for the `webhooks` queue |
| Push | accepted, dispatched, provider failures, queue age |

<Callout type="warn" title="Watch per-channel label cardinality">
Annotation and delta compression metrics are labeled by channel. With many short-lived channels they

### WebSocket delivery metrics

| Metric | Type | Labels | Meaning |
| --- | --- | --- | --- |
| `sockudo_ws_messages_sent_total` | counter | `app_id`, `port` | Application messages addressed to connections. Each node counts only its own local recipients, so `sum` across nodes is the cluster delivery total. Control frames are excluded. |
| `sockudo_ws_control_frames_total` | counter | `app_id`, `port`, `frame_type` | Control frames sent through the connection handler. `frame_type` is one of `pong`, `error`, `connection_established`, `ack`, `auth`, `cache_miss`, `delta_negotiation`, `history`, `other`. |
| `sockudo_ws_message_bytes` | histogram | `app_id`, `port` | Serialized size of each published application message, buckets 64 B to 1 MiB. |
| `sockudo_socket_transmitted_bytes` | counter | `app_id`, `port` | Bytes addressed to connections (message size × recipients). |

How these are counted:

- Deliveries are counted at address time, before the socket write. Delta conflation and tag
  filtering can still skip individual writes, so the counter can slightly exceed actual writes.
  This matches Pusher's addressed-delivery semantics.
- `sockudo_ws_message_bytes` is observed once per published message on the origin node, never on
  receiving nodes or per recipient. It is a per-message size distribution; use
  `sockudo_socket_transmitted_bytes` for total bytes. A Prometheus histogram cannot report `max`.
- Presence `member_added`, `member_removed` and `presence_update` events are counted on remote
  nodes but not on the node that handled the join or leave.
- Server-initiated `pusher:ping` frames are not counted in `sockudo_ws_control_frames_total`.
- A watch on `frame_type="other"` flags new protocol events that need a named `frame_type`.

When `ably-compat` is enabled, two lock-free operator snapshots supplement Prometheus:

- `/operator/stats/ably-runtime` reports queued messages/bytes, overflow and continuity loss,
  total encoded frames, shared data-projection encodes (`data_encoded`), fanout counts, replay
  source and recovery backend calls, duplicate suppression, backend/degraded/reset state, expiry,
  and derived-filter cache pressure. `data_encoded` excludes ACK, heartbeat, connection, and
  channel-control frames, so it is the counter used to verify one encode per active data format.
- `/operator/stats/aggregation` reports the bounded stats queue capacity, backlog, accepted,
  flushed, dropped, and failed observations.

These endpoints expose counters only. They never return credentials, device tokens, channel
payloads, or raw encrypted values.

## AI Transport

AI Transport observability is domain-blind. Sockudo reads only the well-known `extras.ai.transport` headers and never labels metrics by channel, run ID, message ID, or client ID.
Headers are validated once and then passed as a typed borrowed view to metric and webhook
classification. Empty `run-client-id` and `step-client-id` unknown-owner sentinels remain
unchanged on the wire but are treated as absent when deriving an identity.

Metrics exposed at `/metrics` include:

- `sockudo_ai_runs_started_total`
- `sockudo_ai_runs_ended_total{reason}`
- `sockudo_ai_cancel_signals_total`
- `sockudo_ai_active_streams`
- `sockudo_ai_stream_duration_seconds`
- `sockudo_ai_stream_bytes_total`
- `sockudo_ai_messages_rejected_total{code}`
- `sockudo_ai_messages_unparseable_total`
- `sockudo_appends_received_total`
- `sockudo_appends_delivered_total`
- `sockudo_rollup_ratio`
- `sockudo_flush_latency`
- `sockudo_history_recovery_success_total{source}`
- `sockudo_history_recovery_failures_total{code}`
- `sockudo_versioned_message_mutations_total{action,result}`
- `sockudo_versioned_message_retrieval_total{surface,result}`

The four production signals are run outcomes, stream rate, rejects by code, and rollup efficiency. Use `docs/public/grafana/ai-transport-observability.json` as the starting Grafana dashboard.

`sockudo_rollup_ratio` is the number of input appends folded into one delivered frame, so higher
means rollup is saving more fanout. `sockudo_flush_latency` is in milliseconds and should stay near
the configured rollup window.

Active-stream gauges use exact atomic insertion/removal deltas. Tracker entries that never receive
a terminal event expire at the configured AI orphan TTL and decrement the same gauge exactly.
AI lifecycle webhooks are awaited into the configured bounded webhook queue, which supplies
backpressure and retry handling; Sockudo does not spawn an unbounded Tokio task per event or retain
AI events in the optional in-process batching vector.

Dashboard starter panels:

| Panel | Metric |
| --- | --- |
| Active AI streams | `sockudo_ai_active_streams` |
| Run outcomes | `sockudo_ai_runs_started_total`, `sockudo_ai_runs_ended_total` |
| Rejects by code | `sockudo_ai_messages_rejected_total` |
| Rollup efficiency | `sockudo_appends_received_total` vs `sockudo_appends_delivered_total`, `sockudo_rollup_ratio` |
| Rollup latency | `sockudo_flush_latency` |
| Recovery health | `sockudo_history_recovery_success_total`, `sockudo_history_recovery_failures_total` |
| Durable state | `sockudo_history_degraded_channels`, `sockudo_history_reset_required_channels` |
| Push backlog | push queue/status/provider metrics from the push dashboard |

For support escalation, capture the channel, wall-clock time window, verified `clientId`, and first error code before collecting logs. Do not ask customers for provider payloads unless the codec layer explicitly requires them.

## Persist completed AI runs

For Ably-style production persistence, persist completed runs from your backend instead of making Sockudo a domain store:

<Steps>

1. Enable the `ai_run_ended` webhook for the app.
2. On `reason: "complete"`, query the history endpoint for the channel around the webhook time.
3. Select messages with the same `extras.ai.transport.run-id`.
4. Store the reduced transcript in your application database.

</Steps>

```ts {13-15}
app.post("/sockudo/webhooks", async (req, res) => {
  for (const event of req.body.events) {
    if (event.name !== "ai_run_ended" || event.reason !== "complete") continue;

    const history = await sockudo.channelHistory(event.channel, {
      limit: 1000,
      direction: "newest_first",
    });

    await storeCompletedRun({
      runId: event.run_id,
      channel: event.channel,
      items: history.items.filter((item) => {
        return item.message?.extras?.ai?.transport?.["run-id"] === event.run_id;
      }),
    });
  }
  res.sendStatus(200);
});
```

Each history item wraps the delivered message in its `message` field, so AI Transport headers are at
`item.message.extras.ai.transport`. The page `limit` is capped by the channel's history
`max_page_size`; follow `next_cursor` for long runs. Verify the webhook signature before trusting the
event, as described in [Webhooks](/docs/server/webhooks#verify-signatures).

## Logs

Use structured logs for events that operators need to investigate:

```json
{
  "level": "warn",
  "target": "sockudo_push",
  "app_id": "app-id",
  "publish_id": "pub_123",
  "provider": "apns",
  "error": "BadDeviceToken"
}
```

Avoid logging secrets, raw auth signatures, provider tokens, or encrypted payloads. Log filters,
JSON output, and the data-safety policy are in the [logging reference](/docs/reference/logging).

## Alerts

Alert on symptoms operators can act on:

- readiness failures
- adapter connection loss
- rising publish failures
- high auth rejection rate after deploy
- recovery success ratio dropping
- history write failures
- webhook retry backlog
- push queue backlog
- push provider credential failures
- push delivery status callback failures

Starting rules, to tune against your own baseline:

| Alert | Expression | Why it matters |
| --- | --- | --- |
| Cross-node fanout loss | `increase(sockudo_horizontal_transport_messages_dropped_total[5m]) > 0` | Subscribers on some nodes missed messages. |
| Adapter flapping | `increase(sockudo_horizontal_transport_reconnections_total[10m]) > 3` | The adapter link is unstable; expect gaps until it settles. |
| Durable history degraded | `max(sockudo_history_degraded_channels) > 0` for 5m | Recovery and history reads on those channels fail closed. |
| Reset required | `max(sockudo_history_reset_required_channels) > 0` | An operator must reset the stream; it will not heal on its own. |
| History write failures | `increase(sockudo_history_write_failures_total[5m]) > 0` | The history backend is rejecting writes. |
| Recovery failure ratio | `sum(rate(sockudo_history_recovery_failures_total[10m])) / (sum(rate(sockudo_history_recovery_success_total[10m])) + sum(rate(sockudo_history_recovery_failures_total[10m]))) > 0.05` | Reconnecting clients are falling back to full backfill. Break down by `code`. |
| Fanout latency | `histogram_quantile(0.99, sum by (le) (rate(sockudo_broadcast_latency_ms_bucket[5m]))) > 250` | p99 delivery is slower than your SLO. |
| Memory shedding | `max(sockudo_memory_pressure_shedding) == 1` for 2m | The node is refusing new connections. |
| Webhook backlog | `sockudo_queue_depth{queue="webhooks",state="ready"}` above baseline for 10m | Webhook consumers are falling behind or failing. |
| Webhook dead letters | `increase(sockudo_queue_settled_total{queue="webhooks",outcome="dead-letter"}[15m]) > 0` | Events were given up on after all retries. |
| Rate limiting | `sum(rate(sockudo_rate_limit_triggered_total[5m])) by (app_id)` well above baseline | A client or tenant is being throttled. |

<Callout type="tip" title="Alert on ratios, not raw counts">
Raw counters scale with traffic. Ratios such as recovery failures over attempts stay meaningful as
your user base grows and do not page you on a busy day.
</Callout>

## Push status workflow

Push publishes are asynchronous. Store the `publishId` returned by the API when a business workflow needs support visibility.

```ts
const response = await sockudo.publishPush({
  recipients: [{ type: "channel", channel: "orders" }],
  payload: { title: "Order updated", body: "Packed" },
});

console.log(response.publishId);
```

Then inspect status with a signed request, for example through the server SDK:

```ts
const status = await sockudo.getPublishStatus(response.publishId);
```

This calls `GET /apps/{app_id}/push/publish/{publish_id}/status`, which requires push admin.

Status records should be retained long enough for customer support and incident review. Retention is
`push.publish_status_ttl_days` (default `30`).
